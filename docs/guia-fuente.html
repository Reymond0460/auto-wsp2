Agente de WhatsApp con IA para reservas

Cómo replicar en cualquier proyecto de TiforTi el asistente que responde a los clientes por WhatsApp, ofrece horas y agenda en la misma base de datos de la página web.

~US$6–8 / mescosto estimado por cliente pequeño
26 / 26pruebas automáticas de QA aprobadas
~45 minpara montarlo con esta guía

Caso base: StudioBarber (demo) · agente «Brayan» · repos auto-wsp2 (agente) y Servicio-Barber (web). Documento interno de TiforTi — tiforti.cl

1Qué hace la automatización

Un número de WhatsApp Business que contesta solo, 24/7, con el tono del negocio, y que reserva de verdad en la agenda de la web.

Atiende

Saluda, ofrece las 3 horas libres más cercanas a lo que pide el cliente, revisa si una hora específica está libre y propone alternativas.

Reserva

Pide el nombre, toma la hora con el mismo candado que usa la web (nunca dos clientes en la misma hora) y confirma solo si quedó guardada.

Comparte agenda

Lo agendado por WhatsApp aparece ocupado en la web y en el panel de administración (con origen «WhatsApp»), y al revés.

Se mantiene en su rol

Solo habla de la atención (horas, precio, horario, pago). No inventa datos: precio, duración y horario los lee de la web.

Así se ve una conversación real (demo StudioBarber)

Hola
Hola bro! 💈 Sí claro, ¿te sirve mañana martes 17 a las 10:00, 11:00 o 12:00? Si no, dime a qué hora te quieres cortar y reviso ✂️

Perfecto Yaritza! ✅ Tu hora quedó agendada para mañana martes 17 a las 12:00. Por favor sé puntual, ¡te esperamos! 💈🔥

2Cómo funciona por dentro

Clienteescribe por WhatsApp
→
Zernioconecta el número y envía un webhook firmado
→
Railwayagente Python (FastAPI) verifica, agrupa y procesa
→
Claude (Anthropic)entiende y decide qué herramienta usar
⇄
FirebaseFirestore de la web: horario, servicios, horas ocupadas, reservas
  • Responder primero, trabajar después: el webhook contesta 200 al instante y la IA trabaja en segundo plano (Zernio reintenta hasta 7 veces si tarda más de 5 s).
  • Sin duplicados: cada evento se registra; si llega dos veces, se ignora.
  • Mensajes seguidos: espera 6 s y responde todo junto («¿otro día?» + «¿otra hora?» = una respuesta).
  • Memoria: historial de cada cliente en PostgreSQL (Railway).
  • Herramientas de la IA: horas_disponibles, reservar_cita, mis_citas. Cancelar lo hace el dueño desde el panel.

5Paso a paso de la puesta en marcha

Orden recomendado. Lo marcado con 👤 lo hace el dueño de las cuentas; lo demás lo hace Claude.

A · Código (Claude)

  1. Copiar auto-wsp2 (agente) y crear la rama de trabajo.
  2. Escribir config/prompts.yaml con identidad, tono y mensajes clave; ajustar config/business.yaml.
  3. Si la web tiene otra estructura de datos, adaptar agent/agenda_web.py (copia las reglas de js/data.js).
  4. En la web: scripts/crear-demo.js con CON_FIREBASE = true y la sección «Próximas reservas» del panel.
  5. Correr python tests/test_qa.py (debe dar 26/26).

B · Anthropic 👤

  1. platform.claude.com → Settings → API Keys → Crear clave → opción «En otro lugar».
  2. Sin vencimiento (o el plazo más largo). Copiarla una sola vez. Poner límite de gasto.

C · Zernio 👤

  1. Crear cuenta → Connections → WhatsApp → Embedded Signup con el número del negocio (coexistencia: la app Business sigue funcionando).
  2. Settings → API Keys → crear clave sk_…. Inventar un webhook secret distinto de la API key.
  3. Claude obtiene el ZERNIO_ACCOUNT_ID y revisa el estado del número.

D · Railway 👤

  1. New Project → Deploy from GitHub repo → elegir repo y rama.
  2. New → Database → Add PostgreSQL.
  3. Variables en el servicio del agente (no en Postgres) — ver tabla siguiente.
  4. Settings → Networking → Generate Domain. Abrir la URL: debe decir "status":"ok" y "agenda":{"ok":true}.

E · Webhook y Firebase 👤

  1. Zernio → Webhooks → URL https://<app>.up.railway.app/webhook, mismo secret, evento message.received.
  2. Firebase → Configuración → Cuentas de servicio → Generar clave privada → pegar el JSON completo en FIREBASE_CREDENCIALES.
  3. Firestore → Reglas: pegar firestore.rules del repo y Publicar (incluye settings y los correos admin).
  4. Publicar la web: node scripts/crear-demo.js y firebase deploy --only hosting --config firebase.demo.json --project <proyecto>.

Hallazgo pendiente: las reglas publicadas en la consola de Firebase no incluyen la regla settings del repositorio. La web no puede leer «Mi horario» y usa los valores base, mientras el agente (con permisos de administrador) sí lo lee: si el dueño cambia su horario en el panel, la web y el agente podrían ofrecer horas distintas. Solución: pegar firestore.rules en Firestore → Reglas → Publicar.
No cubierto automáticamente: el tono exacto de cada respuesta (lo genera la IA). Se valida con 3 conversaciones reales antes de entregar: pedir hora, pedir una hora ocupada, preguntar algo fuera de tema.

8Problemas que ya resolvimos (y cómo evitarlos)

SíntomaCausa y solución
El agente le responde a todos (familia, pareja)El número es personal (coexistencia). Usar NUMEROS_PERMITIDOS en demos.
Habla con voseo («decime», «tenés»)Indicar en el prompt el país y prohibir el voseo.
Dos respuestas que se contradicenEl cliente mandó 2 mensajes seguidos. Ya se agrupan (6 s).
Repite «bro», precio y duración en cada mensajeReglas de estilo en el prompt: no repetir datos ya dichos; emojis con moderación.
Variables con aviso «Database configuration change»Se agregaron al servicio Postgres. Van en el servicio del agente.
Railway no toma los cambios nuevos«Redeploy» reinstala el mismo commit. Usar Ctrl+K → Deploy latest commit y activar despliegue automático.
La web muestra libre una hora tomadaCaché del navegador con la versión antigua. Ctrl+Shift+R.
Panel: «No se pudo conectar con la base de datos»Correo no autorizado en firestore.rules o reglas sin publicar.
Panel no muestra la reserva de mañanaSolo tenía «Agenda de hoy». Se agregó «Próximas reservas».
Git: «detected dubious ownership»Carpeta en otro disco (D:). git config --global --add safe.directory <ruta>.
La demo guardaba reservas solo en el navegadorMODO_DEMO sin Firebase. crear-demo.js ahora usa CON_FIREBASE = true.
Clave de API escrita en un chat de WhatsAppBorrarla y rotarla. Las claves solo viven en Railway.

Seguridad

  • Las claves (Anthropic, Zernio, cuenta de servicio de Firebase) solo van en Railway. Nunca en GitHub, en el chat ni en WhatsApp.
  • El webhook verifica la firma HMAC de Zernio: sin el secret nadie puede inyectar mensajes.
  • La cuenta de servicio de Firebase tiene acceso total: guardar el archivo en un lugar seguro o borrarlo tras cargarlo.
  • Las reservas por WhatsApp quedan con consent.accepted = false (el cliente no marcó la política de privacidad en la web).
